# Plan: Search + AI Assistant for Incident Triage

Source brief: `incident-triage-take-home.md` · Plan written: 2026-11-06 · Status: **plan only, no code yet**

The brief is evaluated on four things: steering AI tools toward clean maintainable code, handling AI
mistakes and edge cases, robustness/debuggability (correlation id, logs, safe failure modes), and clear,
repeatable docs. Every decision below is made with those four in mind and with a hard 3-hour timebox.

## 1. Decisions made up front (so the build never stalls)

| # | Topic | Decision | Why | Rejected alternative |
|---|---|---|---|---|
| D1 | Language | Python 3.13, FastAPI, Pydantic v2 | Fastest to scaffold in 3h; AI tools produce reliable FastAPI; Pydantic gives validation + docs for free | ASP.NET Core Minimal APIs: equally valid, slower to scaffold. Plan ports 1:1 if needed (Microsoft.Data.Sqlite + Azure.AI.OpenAI). |
| D2 | Search backend | SQLite + FTS5 via stdlib `sqlite3` (porter stemming, bm25 ranking, `snippet()`) | Zero infra (brief says infra isn't evaluated); real relevance ranking; file-backed so ingest survives restarts | Postgres/OpenSearch (docker + setup time); `LIKE` scans (no ranking). |
| D3 | Retrieval type | Lexical only, no embeddings | 300 records; stemming + bm25 is adequate; embeddings add a second external dependency, cost, and time | Hybrid BM25 + embeddings → listed under "2 more days". |
| D4 | LLM access | `openai` SDK; providers `openai`, `azure-openai`, and `fake` (tests/offline only) | One SDK covers both named providers and any OpenAI-compatible base URL; `fake` keeps tests hermetic | Raw httpx (re-implement retries/timeouts); multiple SDKs. |
| D5 | LLM output | JSON mode (`response_format={"type":"json_object"}`) + Pydantic validation + one "repair" retry | Works across OpenAI/Azure/compatible endpoints; strict structured outputs vary by model/API version | Strict structured outputs (nicer, brittle across providers). |
| D6 | Concurrency | Sync `def` endpoints (FastAPI runs them in a threadpool); one short-lived SQLite connection per operation | Simplest correct option; no async DB driver; no shared-connection thread issues | Async everything. |
| D7 | Trace storage | In-memory bounded ring buffer (last 500 correlation ids), thread-safe | Brief says "keep it simple"; process-local limitation is documented | SQLite `traces` table (easy follow-up). |
| D8 | `/assist` with zero hits | Do **not** call the LLM; return a deterministic "nothing relevant, please provide X" response | Cheaper, safer, fully testable; satisfies the grounding rule literally | Let the LLM write the clarifying message. |
| D9 | Citation count | Prompt asks for 3–5; guardrail accepts 1–5, never pads with irrelevant records | Grounding beats quota: padding invents relevance | Force-fill to 3 from search rank. |
| D10 | Ingest source | `DATA_PATH` env (default `data/incidents.json`) **or** inline `incidents` array in the body; never a file path in the request | Prevents arbitrary file reads through the API | `{"path": "..."}` request field. |
| D11 | Severity vocabulary | `low \| medium \| high \| critical` | Reads naturally in prompts and customer text | `sev1..sev4`. |
| D12 | Tags filter semantics | `tags=a,b` (or repeated `tags=`) means **all** tags must be present | Predictable narrowing; documented in README | any-of semantics. |
| D13 | Query mode | Try AND of all terms first; if 0 hits, fall back to OR; response reports `match_mode` | Precise when possible, forgiving for natural-language questions in `/assist` | OR only (inflated hit counts); AND only (NL questions get 0 hits). |

## 2. Architecture

### 2.1 Request flow

```
client ──HTTP──▶ CorrelationIdMiddleware (read/generate X-Correlation-ID, set ContextVar, access log)
                  │
                  ├─ POST /ingest ──▶ IngestService ──▶ SearchStore.upsert_many ──▶ SQLite (incidents, incident_tags, incidents_fts)
                  ├─ GET  /search ──▶ SearchService.search ──▶ QueryBuilder ──▶ SearchStore.search
                  ├─ GET  /incidents/{id} ──▶ SearchStore.get
                  ├─ POST /assist ──▶ AssistService
                  │                     1. tool:search  = SearchService.search  (SAME function the /search route calls)
                  │                     2. zero hits? → deterministic "needs more info" response (no LLM call)
                  │                     3. build prompt (system rules + rendered candidates)
                  │                     4. llm:complete = LLMClient.complete_json (timeout, 1 repair retry)
                  │                     5. guardrails   = pure functions (citations ⊆ candidates, evidence check, id scrub, cap 5)
                  │                     6. selected ids → response ; every step → TraceRecorder + log line
                  ├─ GET  /debug/trace/{correlation_id} ──▶ TraceRecorder.get
                  └─ GET  /health ──▶ store count + llm configured flag
```

## 3. Data: synthetic incident generator

**Output**: `data/incidents.json` (300 records), committed. Generator also committed so reviewers can regenerate.

**Determinism**: single `random.Random(seed)` instance, seed default 42, no `datetime.now()` inside the generator
(use a fixed anchor date `2026-11-01T00:00:00Z` and go back up to 180 days). Records sorted by `created_at`
then assigned ids `INC-0001..INC-0300`, so ids are monotonic in time.

**Record shape** (exactly the brief's fields):

```json
{
  "id": "INC-0042",
  "created_at": "2026-08-14T03:21:00Z",
  "environment": "prod",
  "service": "checkout",
  "severity": "high",
  "title": "checkout returning 5xx: database connection pool exhausted",
  "description": "Starting 03:10 UTC, checkout p99 latency rose from 220ms to 4.8s and 5xx rate reached 12%. Logs show 'SQLSTATE 53300 too_many_connections' from pg-primary-1. A deploy of v2024.08.3 at 02:58 doubled worker count without raising the pool limit.",
  "resolution_summary": "Rolled back to v2024.08.2, then raised pool_max from 20 to 50 and added a worker-count/pool-size invariant check to CI. Follow-up: alert on pool saturation > 80%.",
  "tags": ["database", "connection-pool", "5xx", "deploy"]
}
```

**Realism strategy**: ~22 incident *archetypes*, each with title/description/resolution templates with slots
(`{service}`, `{dependency}`, `{region}`, `{version}`, `{pct}`, `{minutes}`, `{error}`), a base severity, and a tag set.
Templates include concrete, searchable details (error strings, HTTP codes, metric names) so searches produce
meaningful clusters. Archetype list to implement:

1. DB connection pool exhausted · 2. TLS certificate expired · 3. Disk full on nodes · 4. OOMKilled after deploy ·
5. Bad release → error spike → rollback · 6. DNS resolution failures · 7. Upstream 429 rate limiting ·
8. Queue/consumer backlog · 9. Cache restart → thundering herd · 10. Schema migration lock blocks writes ·
11. Clock skew → JWT validation failures · 12. Config typo → crash loop · 13. Third-party vendor outage ·
14. Slow memory leak / periodic restarts · 15. Retry storm amplifying an outage · 16. Feature flag misconfiguration ·
17. Read-replica lag → stale reads · 18. Overlapping cron jobs · 19. Payment gateway timeouts ·
20. Stale search index after reindex failure · 21. Log pipeline dropping events · 22. Autoscaler failed to scale out.

Pools: 12 services (`checkout, payments, auth, search-api, notifications, inventory, billing, api-gateway,
user-profile, reporting, cdn-edge, scheduler`), environments weighted prod 45% / stage 20% / qa 20% / dev 15%,
severity drawn from archetype base ± noise (prod skews higher), ~25 tags total (archetype tags + 0–1 random extra).

**Validation of the dataset** (test): 300 records, unique ids, enums valid, all fields non-empty,
`generate(seed=42)` called twice yields byte-identical JSON.

## 4. Search design (SQLite FTS5)

### 4.1 Schema

```sql
CREATE TABLE IF NOT EXISTS incidents (
  id TEXT PRIMARY KEY,
  created_at TEXT NOT NULL,                 -- ISO 8601 UTC
  environment TEXT NOT NULL CHECK (environment IN ('dev','qa','stage','prod')),
  service TEXT NOT NULL,                    -- stored lowercased
  severity TEXT NOT NULL CHECK (severity IN ('low','medium','high','critical')),
  title TEXT NOT NULL, description TEXT NOT NULL, resolution_summary TEXT NOT NULL,
  tags_json TEXT NOT NULL,                  -- sorted, lowercased JSON array (for output)
  content_hash TEXT NOT NULL,               -- sha256 of canonical record → idempotency
  ingested_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS ix_incidents_env ON incidents(environment);
CREATE INDEX IF NOT EXISTS ix_incidents_service ON incidents(service);
CREATE INDEX IF NOT EXISTS ix_incidents_severity ON incidents(severity);
CREATE TABLE IF NOT EXISTS incident_tags (
  incident_id TEXT NOT NULL REFERENCES incidents(id) ON DELETE CASCADE,
  tag TEXT NOT NULL, PRIMARY KEY (incident_id, tag));
CREATE VIRTUAL TABLE IF NOT EXISTS incidents_fts USING fts5(
  id UNINDEXED, title, description, resolution_summary, tags,
  tokenize = 'porter unicode61');
```

Deliberately a *regular* FTS5 table (not external-content + triggers): duplication is irrelevant at 300 rows and it
removes the trigger-sync class of bugs (a known AI-generation hotspot). The FTS row is deleted+inserted by id inside
the same transaction as the `incidents` upsert.

Startup (`lifespan`): `PRAGMA journal_mode=WAL`, create schema, and probe FTS5 by creating a temp virtual table;
if FTS5 is missing, fail startup with a message naming the fix (use the uv-managed Python).

### 4.2 Query builder (`search/query.py`, pure, unit-tested)

`build_fts_query(q: str) -> FtsQuery | None` where `FtsQuery` has `all_terms: str` and `any_terms: str`.

1. Lowercase; replace every character that is not a letter/digit with a space (this neutralises all FTS5 operators:
   `" * - : ( ) ^ NEAR OR AND NOT`).
2. Split; drop tokens shorter than 2 chars; drop a ~40-word stop list (`the a an is are was in on of for to why what how
   when with and or not our we it this that from into after before...`).
3. Keep at most 12 tokens (limit).
4. Each token becomes `"token"` (double-quoted literal) → `all_terms = '"t1" AND "t2"'`, `any_terms = '"t1" OR "t2"'`.
5. Nothing left → `None` → caller treats as "no text query" (filter-only browse ordered by `created_at DESC`).

Porter stemming happens inside FTS5 for both index and query, so `timeouts`/`timing out`/`timed out` meet.

### 4.3 Search SQL (`sqlite_store.py`)

```sql
SELECT i.id, i.title, i.environment, i.service, i.severity, i.created_at,
       snippet(incidents_fts, 2, '', '', '…', 24) AS snippet,         -- col 2 = description
       -bm25(incidents_fts, 0.0, 3.0, 1.0, 1.0, 2.0) AS score         -- weights: id,title,description,resolution,tags
FROM incidents_fts f JOIN incidents i ON i.id = f.id
WHERE incidents_fts MATCH :match
  AND (:environment IS NULL OR i.environment = :environment)
  AND (:service     IS NULL OR i.service     = :service)
  AND (:severity    IS NULL OR i.severity    = :severity)
  AND (:n_tags = 0 OR i.id IN (SELECT incident_id FROM incident_tags WHERE tag IN (...)
                               GROUP BY incident_id HAVING COUNT(DISTINCT tag) = :n_tags))
ORDER BY bm25(...) LIMIT :limit OFFSET :offset;
```

plus a `SELECT COUNT(*)` with the identical WHERE for `total`. bm25 is negative-is-better; expose `score = -bm25`
rounded to 3 decimals so bigger is better for API consumers. Two-phase execution per D13: run with `all_terms`;
if `total == 0`, rerun with `any_terms` and set `match_mode="any"`. Filter-only browse (no `q`) skips FTS and
orders by `created_at DESC`; snippet = first 160 chars of description.

### 4.4 `GET /search` contract

Query params: `q` (optional, ≤500 chars), `environment` (enum), `service` (≤64 chars, case-insensitive),
`severity` (enum), `tags` (comma-separated or repeated; ≤10; all-of), `limit` (1..50, default 10), `offset` (0..1000).
At least one of `q` or a filter is required; otherwise 422 with a helpful message.

```json
{
  "query": "connection pool exhausted", "filters": {"environment": "prod", "service": null, "severity": null, "tags": []},
  "match_mode": "all", "total": 7, "limit": 10, "offset": 0,
  "results": [{"id": "INC-0042", "title": "...", "snippet": "...", "score": 9.812,
               "environment": "prod", "service": "checkout", "severity": "high", "created_at": "..."}],
  "correlation_id": "..."
}
```

### 4.5 `GET /incidents/{id}`

Validate id against `^[A-Za-z0-9_-]{1,64}$` (422 otherwise); 404 with the error envelope if unknown; returns the full
record exactly as ingested (tags as array).

## 5. Ingest design

`POST /ingest` body is optional: `{}` / absent → load `DATA_PATH`; `{"incidents": [...]}` → use the body
(max `MAX_INGEST_RECORDS`=5000, body ≤ 2 MB via a Content-Length check → 413).

Algorithm (one connection, one transaction, all-or-nothing):
1. Validate every record with the `Incident` model (normalise: service lowercased, tags lowercased/stripped/deduped/sorted,
   naive `created_at` assumed UTC). Any invalid record → 422 listing up to 20 `{index, id, error}` entries.
2. Duplicate ids inside the batch → 422 ("ambiguous: INC-0007 appears twice").
3. `content_hash = sha256(canonical JSON of normalised record)`.
4. For each record: no row → INSERT (`ingested`); same hash → `skipped`; different hash → UPDATE incidents, replace
   tag rows, delete+insert FTS row (`updated`).
5. Response: `{"ingested": 300, "updated": 0, "skipped": 0, "total_in_store": 300, "source": "data/incidents.json", "correlation_id": "..."}`.

Idempotency proof in tests: run twice → `{0 ingested, 0 updated, 300 skipped}`, FTS row count == incidents row count.

## 6. Assist design

### 6.1 Request / response

`POST /assist` body: `{"question": "...", "environment"?, "service"?, "severity"?, "tags"?: [..], "top_k"?: 3..5}`.
`question` 3..2000 chars (configurable). Filters reuse the `SearchFilters` model from `/search`.

```json
{
  "correlation_id": "…", "status": "ok",                          // or "no_relevant_incidents"
  "question": "…", "filters": {…},
  "relevant_incidents": [
    {"id": "INC-0042", "title": "…", "why_relevant": "…", "evidence_quote": "…", "evidence_verified": true}
  ],
  "next_steps": ["…"],
  "customer_response": "…",
  "clarifying_questions": [],                                        // populated when status != ok
  "retrieval": {"hit_count": 17, "match_mode": "any", "candidate_ids": ["INC-0042", "…"]},
  "llm": {"provider": "openai", "model": "gpt-4o-mini", "latency_ms": 1240, "attempts": 1},   // null when LLM not called
  "warnings": ["model cited unknown id INC-9999; dropped"]
}
```

### 6.2 Pipeline (each numbered step is a trace step + a log line)

1. `request` — question length, filters.
2. `tool:search` — input summary `{query, filters, limit: ASSIST_CANDIDATE_LIMIT=8}`; output summary
   `{hit_count, top_ids, match_mode, duration_ms}`. Calls `SearchService.search(...)`, nothing else.
3. Zero candidates (or question reduced to no searchable terms) → `status="no_relevant_incidents"`,
   `clarifying_questions` = fixed list (service, environment, exact error text, time window, user impact),
   `customer_response` = a safe generic holding message, `llm = null`. **No LLM call.** Return 200.
4. `llm:complete` — build messages (6.3), call `LLMClient.complete_json(system, user, timeout)`; parse to
   `LLMAssistOutput`. On JSON/schema failure: one repair attempt that appends the validation error and asks for
   JSON only. Trace `{provider, model, prompt_chars, attempts, latency_ms, usage?}`.
5. `guardrails` — pure functions over (output, candidate records), see 6.4. Trace what was dropped/scrubbed.
6. `selected` — final incident ids. Then assemble the response (titles are taken from the store, not the model).

### 6.3 Prompt (draft; final text lives in `assist/prompts.py`)

System (contains the word "JSON", required by OpenAI JSON mode):

```
You are an incident triage assistant for an on-call engineering team.
You receive a QUESTION and a list of RETRIEVED INCIDENT RECORDS. Rules:
1. Use ONLY information present in the retrieved records. Never invent incident details, numbers, dates, causes, or fixes.
2. Cite incidents only by ids that appear in the retrieved records, exactly as written (e.g. INC-0042).
3. Select the 3 to 5 most relevant records. If fewer than 3 are genuinely relevant, return only those.
   If none are relevant, return an empty list, set needs_more_info to true and ask specific clarifying questions.
4. For every cited record include evidence_quote: a short phrase copied verbatim from that record.
5. next_steps are concrete actions grounded in the cited records' resolutions; label general best practices as such.
6. customer_response is polite, non-technical, must not mention incident ids, internal service names,
   unconfirmed root causes, or promise timelines.
Respond with a single JSON object and nothing else, matching:
{"relevant_incidents":[{"id":"...","why_relevant":"...","evidence_quote":"..."}],
 "needs_more_info":false,"clarifying_questions":[],"next_steps":["..."],"customer_response":"..."}
```

User message: `QUESTION`, `FILTERS`, then candidates rendered compactly
(`[n] id=… | created_at=… | env=… | service=… | severity=… | tags=…` + title / description (≤600 chars) /
resolution_summary (≤400 chars)). 8 candidates ≈ 2–3k tokens. `temperature=0`, `max_tokens=900`.

### 6.4 Guardrails (`assist/guardrails.py`, pure, unit-tested — the brief's hard requirement)

| Guardrail | Behaviour | Test |
|---|---|---|
| Citations ⊆ candidates | Any cited id not in the retrieved set is dropped and reported in `warnings` | yes |
| Cap | At most 5 citations, order preserved | yes |
| Evidence check | `evidence_quote` must be a substring of the record (lowercased, whitespace-collapsed, punctuation-stripped, ≥8 chars). Mismatch → keep the citation but `evidence_verified=false` + warning (models paraphrase; dropping would be too lossy) | yes |
| Foreign ids in prose | Regex `\bINC-\d{4,}\b` over `why_relevant`, `next_steps`, `customer_response`; ids outside the selected set are replaced with `[removed]` + warning | yes |
| Customer text | No incident ids at all; ≤1500 chars | yes |
| Empty after filtering | → `status="no_relevant_incidents"` path with the model's clarifying questions (or defaults) | yes |

Two honest caveats to state in TRADEOFFS.md: (a) the evidence check verifies a quote, not every claim, so paraphrased
fabrication inside `why_relevant` is still possible, mitigated by temperature 0 and the system rules; (b) `next_steps`
are not verified against records beyond id scrubbing.

### 6.5 LLM client layer (`llm/`)

```python
class LLMClient(Protocol):
    provider: str; model: str
    def complete_json(self, system: str, user: str, *, timeout_s: float) -> LLMResult  # text, latency_ms, usage
```

Error hierarchy → HTTP mapping (handled centrally in `api/errors.py`):

| Exception | When | HTTP | `code` | `how_to_fix` (example) |
|---|---|---|---|---|
| `LLMNotConfigured` | provider needs a key and `LLM_API_KEY` is empty, or Azure endpoint missing | 503 | `llm_not_configured` | "Set LLM_API_KEY (and LLM_PROVIDER=openai, LLM_MODEL=gpt-4o-mini), e.g. `export LLM_API_KEY=sk-...` then restart `uv run uvicorn app.main:app`. Search and ingest work without it." |
| `LLMAuthError` | 401/403 from provider | 502 | `llm_auth_error` | "LLM_API_KEY was rejected; check the key/project. For Azure also check AZURE_OPENAI_ENDPOINT and the deployment name in LLM_MODEL." |
| `LLMTimeout` | SDK timeout | 504 | `llm_timeout` | "Timed out after N s; retry or raise LLM_TIMEOUT_SECONDS." |
| `LLMRateLimited` | 429 | 429 | `llm_rate_limited` | "Retry after a moment or use a different model." |
| `LLMBadOutput` | invalid JSON/schema after repair retry | 502 | `llm_bad_output` | "Model did not return valid JSON; see /debug/trace/{cid}; try another LLM_MODEL." |
| `LLMUpstreamError` | any other provider error | 502 | `llm_upstream_error` | message from provider, no secrets |

`factory.build_llm_client(settings)` is invoked per request through a dependency, so a missing key breaks only
`/assist` (clear 503), never startup or `/search`. `FakeLLMClient` parses `id=INC-…` lines out of the prompt and
returns a valid JSON citing the first three with verbatim title quotes; it can be configured to raise
`LLMTimeout`, return garbage, or cite a bogus id, which is how error paths and guardrails are tested end-to-end.
`LLM_PROVIDER=fake` is documented as **tests/offline only** and does not satisfy the "real LLM" requirement.

## 7. Observability

- **Correlation id**: pure-ASGI middleware (not `BaseHTTPMiddleware`, which has contextvar/streaming quirks) reads
  `X-Correlation-ID`; accepted if it matches `^[A-Za-z0-9._:-]{1,128}$`, else a `uuid4` is generated. Stored in a
  `ContextVar`, echoed back as a response header, included in every JSON error body.
- **Logging**: stdlib `logging`; a `Filter` injects `correlation_id` (or `-` outside a request) into every record;
  JSON formatter (`ts, level, logger, correlation_id, message, + extras`) or `text` for local dev (`LOG_FORMAT`).
  Uvicorn's own access log is disabled and replaced by the middleware's access line
  (`method path status duration_ms`), so **every** line carries the id. Uvicorn error logs are routed through the
  same handler.
- **Trace recorder**: `TraceRecorder.add(cid, Step(name, ts, duration_ms, input, output))`, bounded `OrderedDict`
  (500 entries, `TRACE_MAX_ENTRIES`), guarded by a lock. `/assist` records `request`, `tool:search`, `llm:complete`,
  `guardrails`, `selected`, `response`. `GET /debug/trace/{cid}` returns `{correlation_id, steps[]}` or 404; can be
  disabled with `DEBUG_TRACE_ENABLED=false`. Never stores API keys or full prompts (prompt length only; full prompt
  at DEBUG log level).
- **Health**: `GET /health` → store backend + incident count, llm provider/model/configured flag, version.

## 8. Robustness: validation, limits, timeouts

| Concern | Measure |
|---|---|
| Input validation | Pydantic models for every body/query param; enums for environment/severity; lengths capped (q ≤500, question ≤2000, id ≤64, tags ≤10×40, limit ≤50, offset ≤1000) |
| Useful errors | Single error envelope with `code`, `message`, `how_to_fix`, `correlation_id`, `details`; `RequestValidationError` re-shaped into it |
| Body size | Content-Length guard middleware (2 MB) → 413; `MAX_INGEST_RECORDS` → 422 |
| External timeouts | OpenAI SDK `timeout=LLM_TIMEOUT_SECONDS` (30s), `max_retries=1`; SQLite `timeout=5` for busy locks |
| Unknown failures | Generic handler → 500 `internal_error` with correlation id, stack trace only in logs |
| Safe degradation | `/search` and `/ingest` never depend on the LLM; `/assist` fails closed with instructions |
| Secrets | API key never logged or echoed; `/health` reports `configured: true/false` only |

## 13. Risks and mitigations

| Risk | Mitigation |
|---|---|
| No LLM key at build/demo time | `/assist` returns a 503 with exact instructions; tests use `fake`; obtain key before 1:15 slot |
| FTS5 `MATCH` syntax errors on user input | Query builder strips everything but letters/digits and quotes every token; tested |
| Model returns prose instead of JSON | JSON mode + "JSON" in system prompt + one repair retry + `llm_bad_output` with trace pointer |
| Model cites ids that don't exist / hallucinated details | Subset guardrail, evidence quote check, id scrub, titles taken from store; prompt rules; temperature 0 |
| OR-fallback inflates `total` for `/search` | `match_mode` is returned so consumers know; AND tried first |
| SQLite threading / locking | Connection per operation, WAL mode, `timeout=5`; ingest is a single transaction |
| In-memory traces lost on restart / multi-worker | Documented; single-worker uvicorn in README; SQLite table listed under "+2 hours" |
| Python 3.9 picked up by accident | `requires-python = ">=3.12"` in `pyproject`, README says `uv run` |
| Time overrun on docs | Prompt log kept from minute 0; README curls recorded while testing the error pass |
| AI-generated code mixing Pydantic v1/v2 or openai v0/v1 APIs | Pin versions in `pyproject`; review every diff; run tests after each prompt |

## 15. Explicitly out of scope (feeds TRADEOFFS.md)

**Not done by design (3h)**: embeddings/hybrid retrieval; auth on the API; persistence of traces; multi-worker
deployment; streaming responses; Anthropic/other provider classes (interface supports them); UI; Docker file
(may add if the docs slot finishes early, it's 10 lines).

**Known limitations to state**: lexical search misses synonyms the stemmer doesn't cover; evidence check verifies a
quote not every claim; OR fallback can inflate totals; in-memory trace is per-process; `/ingest` is all-or-nothing
(no partial success report); dataset is synthetic and templated, so near-duplicate incidents exist by construction.

**+2 hours**: SQLite-backed traces; `test_filters` edge cases (offset beyond total, unicode queries); Dockerfile;
`GET /search` highlight markers; rate limiting on `/assist`; eval script that runs 10 questions and reports
citation-validity and evidence-verified rates.

**+2 days**: hybrid retrieval (bm25 + embeddings with reciprocal rank fusion) behind the same `SearchStore`
interface; Postgres store implementation; prompt/eval harness with golden answers; incident clustering to suggest
"similar past incidents" on ingest; OpenTelemetry export of the trace steps; CI workflow (ruff + pytest).
